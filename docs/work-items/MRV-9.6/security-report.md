# Security report MRV-9.6 (delivery address choice)

**Verdict: PASS.** No critical or high finding. Two low and four informational notes; none blocks. Read-only review of the uncommitted change set (API, domain, EF model, migration, migration-delivery.sh, seed-demo.mjs, SPA picker/coverage call). Tests were not run.

## Checked and sound
1. Authorization and ownership. `DeliveryAddressChoice.ResolveAsync` looks the address up by key AND owner (`ClientAccountId`), so a foreign or unknown key is 404 on all four paths. Quote PUT finds the quote by number AND `ClientAccountId` (someone else's quote is 404); staff and anonymous callers get 403/401 (matrix rows added). Employee order create/amend resolve the key against the customer of the order (`order.ClientAccountId` / `request.ClientId`), so staff cannot use another customer's key. Billing-only is a 400 only after ownership is proven, so it reveals nothing. Pending/Suspended customers get 403 on create and on change; an unapproved customer cannot get an order via staff (403 kept). Ordering on the customer PUT: ownership, then eligibility, then key, then status (a 409 for an Accepted quote only follows a valid own key; no existence leak).
2. Races. `Quote.Status` and `Quote.DeliveryAddressId` are concurrency tokens; accept, reject, price and change all catch `DbUpdateConcurrencyException` and answer 409. Two accepts: the second fails on the Status token (no second order). The order is built and saved in the same SaveChanges as the quote flip, so the snapshot is complete or absent.
3. Snapshot integrity. Requests carry only a key (`ChangeDeliveryAddressRequest`, `CreateQuoteRequest`, `CreateEmployeeOrderRequest`); the snapshot is always copied server side from the DB row, so no mass assignment of address text. Column lengths match the address rules. The DTO has no key or id (`DeliveryAddressSnapshotDto`). Editing/deleting an address leaves documents unchanged (FK SET NULL, copy stays).
4. Audit. Order amend writes before/after (label and one-line address), order number and customer number in the same save as the change (`TrySaveAsync`; failure is 409). Details are serialized as JSON and rendered by Angular (escaped). Address text in the audit is personal data, same class as the existing audited address changes; acceptable.
5. Rate limit. Both new PUTs carry `addresses` (per IP, 60/min default). Create endpoints reuse their existing policies. `UseRateLimiter` runs before auth (existing project pattern: per-IP bucket, so unauthenticated floods share the bucket of a NAT).
6. DTOs/views. Snapshot is only in the owner's own quote/order DTOs and in staff views; no customer sees another customer's addresses. No new endpoint lists addresses.
7. Migration. Only nullable column additions, SET NULL FKs, indexes; Down drops only the new objects and keeps `orders.delivery_address`; no backfill, so no data loss on Up. Script binds `127.0.0.1:55436`, uses a throwaway container and password, removes the container via trap.
8. SPA. No `innerHTML`/`bypassSecurity*`; all address text is interpolated. `<option [value]="address.key">` only carries the customer's own address key (never shown). Coverage failure is handled and non-blocking; the result is dropped when another address is chosen.

## Findings
| # | Severity | Location | Risk | Fix |
|---|---|---|---|---|
| F-1 | Low | `EmployeeOrdersController.Create` legacy fallback (`request.DeliveryAddress?.Trim()`) and `Order.DeliveryAddress` (no `HasMaxLength` in `AppDbContext`) | Staff-supplied free text for a customer with no structured address is stored unvalidated: no length cap (body limit is the only bound), control/newline characters allowed. It is later shown to the customer and used in logs/audit "Before". Staff-only and one-release fallback, so exploitation needs a malicious employee. | Reject text over 500 chars and strip/refuse control characters (reuse the address text rules from MRV-9.3) before storing; optionally `HasMaxLength(600)` on the column. |
| F-2 | Low | `AppDbContext` concurrency tokens vs `QuotesController.Accept` | If the customer re-picks the SAME address (after editing it) while an accept runs, `DeliveryAddressId` does not change and only the text columns differ, so the accept can succeed with the old snapshot copied to the order while the quote now shows the new text. Narrow window; no foreign data involved; the order carries the address the customer had accepted against a moment earlier. | Make a row version (`xmin`) the token, or add the snapshot fields to the concurrency tokens. |
| I-1 | Info | `Quote.DeliveryAddressId` as token | When an address is deleted, SET NULL changes the row behind a loaded quote, so one stale accept/price gets a spurious 409 (reload fixes it). | Acceptable; message already says reload. |
| I-2 | Info | `EmployeeOrdersController.ChangeDeliveryAddress` | `Order.Status` has no concurrency token. No endpoint ships or cancels orders yet, so no race today; if one is added, shipping vs amend could pass. | Add a token on `Order.Status` when fulfilment lands. |
| I-3 | Info | `delivery-picker.ts` coverage check | The formatted address (street, number, complement, district, city, state, CEP; not the notes) is POSTed to the anonymous `/api/coverage/check` and from there to the geocoding provider (Google/Azure). It is in the body, not the URL, and the server does not log it. The UI does not say that a third party receives it. | Add a one-line notice next to the button (and in the privacy text) that the address is sent to the map provider; owner decision. |
| I-4 | Info | `test/runtime/migration-delivery.sh` | `docker run` with the published port happens before `trap` is set: if port 55436 is taken, the failed container is left until the next run (the script removes it at start). The connection string with the throwaway password is on the `dotnet ef` command line. | Move `trap` before `docker run`; harmless otherwise. |

## Standing notes (MRV-9.3/9.4) honored
Stored free text is escaped on output (Angular, no raw HTML); ownership by key and owner with 404 for foreign keys; new write endpoints reuse the `addresses` rate-limit policy.
