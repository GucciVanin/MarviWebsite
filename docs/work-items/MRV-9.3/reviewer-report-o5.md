## Special question: the `.table-wrap` scrollLeft reset in `test/layout/audit.mjs` (`openStep`)

A legitimate diagnosis, but I would not keep the fix in that form.

- The finding is a measurement artefact. `rules.mjs` container-edge block (~lines 318-337) compares each child's left edge to the parent's content edge; `.table-wrap` matches `/wrap/`, and the scroll-container exemption (`isScroller`) is applied to `exceeds-parent` only. A table inside a scroller that was scrolled sideways (here by focus moving into the fix form, which sits inside the customers table, admin-customers.html:23-123) always has `left < content edge`. The page does not overflow: `overflow-page`, `overflow-element` and `exceeds-parent` still run on the same load and are at 0 (0/264).
- It does not weaken the fixtures: `container-edge.html` and the others run `auditDom` directly, never through `openStep`, and the diff leaves `rules.mjs` and the fixtures untouched, so container-edge violations are still caught. (I did not re-run the self-test.) The reset touches only `.table-wrap`, only after a `#step` click.
- Weaknesses: (a) it patches the harness rather than the rule, so container-edge stays wrong for any real, user-scrolled table (exceeds-parent is already scroll-aware per docs/tests/layout-audit.md:39); (b) it audits the form at scroll 0, a state a keyboard user never sees (the browser scrolls the focused field into view), so a field clipped at 320 px inside the table is judged only at scroll 0; (c) hard-coded class name; (d) undocumented.
- What I would change: make container-edge scroll-aware in `rules.mjs` (skip a child whose parent is a scroll container, or compare `r.left + parent.scrollLeft`), add a fixture with a scrolled `.table-wrap` that must stay clean while `container-edge.html` stays flagged, remove the reset from `audit.mjs`, document it in layout-audit.md, and optionally assert that the focused field is inside the viewport after `openStep` (the real keyboard check). Separate UX note: the address fix form living in a horizontally scrolling table at 320/375 px is awkward; that is pre-existing design, not an O-5 regression.
