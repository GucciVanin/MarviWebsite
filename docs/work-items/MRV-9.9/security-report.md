# Security report MRV-9.9

**Verdict: pass.** No critical or high findings. Read-only review of the uncommitted change set; nothing was run.

## Findings
1. **Low (pre-existing, not widened): login timing for unknown e-mail.** AuthController.Login returns 401 before `CheckPasswordAsync` when the e-mail is unknown, so no hash is computed there; known-wrong-password pays a hash. This allows timing enumeration of registered e-mails, but is unchanged by this story. The 401 status/body/headers are identical for every case. Fix (separate story): verify against a dummy hash for unknown users.
2. **Low: cache cap behaviour.** At 10,000 entries `Purge` drops expired entries and then `Clear()`s everything (a thundering herd of DB reads, and a null for a missing account is cached too). Keys come only from signed tokens (`client_id` claim), so an attacker cannot mint random ids; the key space is bounded by real customers. Not exhaustible by an outsider; the cap bound is untested (acknowledged in decisions.md). Fix if desired: evict instead of clear.
3. **Low: fail-closed on error, availability only.** If the DB read throws in the gate, nothing catches it, so the request ends in a 500 (a suspended customer is never let through). Note a DB outage already breaks the API; acceptable. A cache entry is never written on failure.
4. **Info: multi-replica / direct-DB lag up to 60 s.** Accurately documented (decisions.md, pr-notes.md). Only Suspend and Approve in AdminClientsController change status (grep: no other writer of `ClientAccountStatus`; registration creates Pending); both call `Invalidate` after the audited save. Race between a read in flight and an invalidation is covered by the generation re-check (reasoning sound; the `Clear()` does not bump the generation but only removes data, which is safe).
5. **Info: deleted customer or token with no/unknown client claim.** The gate only looks up Client-role tokens with a `client_id`; a missing account caches as null and passes the gate (the endpoint's own authorization then applies, as before). Employee, Admin, visitor tokens never touch the cache. Mid-request status change: the request that passed the gate completes, as with any token check (bound: one request).

## Checks per focus area
1. **Login:** the 403 is returned only after `CheckPasswordAsync` succeeds and the role is Client with a Suspended account. Wrong password for unknown, Pending, Approved, Suspended: the same `Unauthorized()` before any status read, so status, body and headers match (tests and runtime compare them, minus traceId). Identity lockout is not used (CheckPasswordAsync does not count failures); the `auth` rate limit applies per endpoint and the 403 takes one permit like any attempt (test exists). A suspended user with the correct password learns only that the account is suspended, which the owner chose to tell after authentication. Nothing logged. Note: the correct-password probe does confirm "suspended" to someone who already knows the password, intended.
2. **Gate:** registered after `UseAuthentication`, before `UseAuthorization` and `MapControllers`, so it covers every controller route, health and anything else in the pipeline (no SignalR or Swagger found in Program.cs; static files are served by nginx). Identity comes from the validated JWT (`IsInRole(Client)` plus `ClientId()` claim; signed, lifetime checked, ClockSkew zero), nothing client-controlled. `/api/auth/*` is exempt by `StartsWithSegments` (case-insensitive); the auth endpoints carry no session data worth protecting (register/login only).
3. **Cache:** `ConcurrentDictionary`, `Interlocked` generation, 60 s lifetime on `TimeProvider` (System in production via TryAddSingleton; replaced only in tests). Thread-safe; concurrent duplicate DB reads are harmless.
4. **Deviation (gate on public endpoints too):** acceptable and stricter. The signed-in SPA sees 403 on `GET /api/products` and signs out; a visitor view is available signed out. No data leak.
5. **SPA:** interceptor reacts only to 403 with `code === 'account_suspended'`, ignores URLs ending in `/api/auth/login`, calls `setToken(null)` (localStorage cleared) and navigates to a fixed `/login` (no user-controlled redirect). The message is a constant from `PT` (not taken from the response body), rendered through Angular bindings (escaped). No sign-out loop: after the token is gone no request carries it; login page does not call authenticated APIs. Minor: `endsWith('/api/auth/login')` would not match a query string, none is used.
6. **Scripts:** runtime test replaces SQL reinstatement with the API approve; the SQL status change in the 60 s test is on the throwaway runtime DB and uses a UUID from the API, no injection from external input. The credentials in layout scripts are the existing public demo test credentials (`*.demo.marvi.test`), no new outbound calls. `test/client.sh` and `test/bundle-size.sh`: no secrets, `docker run --rm`, client mounted read-only, quoted variables, `set -euo pipefail` in bundle-size, exit codes kept (`client.sh` exits with the ng code or 1 on an Errors line). Image argument is only passed to `docker run`.
7. **Docs vs code:** 60 s bound, immediate invalidation on the same process, multi-replica lag and direct-DB lag all match the code.
