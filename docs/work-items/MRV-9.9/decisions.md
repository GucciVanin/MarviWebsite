# decisions
- 2026-11-03 Owner: total bundle cap raised to 300 kB (300,000 B by the gzip -9 -n -c per-file method over js+css, island excluded; was 237,975 B = 177,975 + 60 kB). The Captain also asks that the first-visit download (initial chunks for `/`) be measured and reported, not gated.
- Login message only after the password is verified (no enumeration of suspended e-mails).
- Standing rule: the client suite counts as green only with exit code 0 and no `Errors` line (see docs/tests/README.md); capture the exit code, do not pipe through tail.
- Worker 2026-11-03, design: the 403 gate is a middleware (`SuspendedClientGate`) after authentication, not a JWT event, so it can answer a body with a machine-readable code (`account_suspended`) the SPA tells apart from a role 403. It applies to every request that carries a Suspended customer's token, public endpoints included (the old token is refused on `GET /api/products` too; a signed-out person sees the visitor view), except `/api/auth/*`, which carry no session (so another person can sign in from a browser holding an old token). Only Client tokens with a `client_id` are looked up; Employee, Admin and visitors never touch the cache.
- Cache (the in-flight race is closed by re-checking the generation after the write, not proven by a deterministic test; the 10,000-entry bound is untested): `ClientStatusCache`, singleton, `ConcurrentDictionary`, entries valid 60 s on `TimeProvider` (the tests replace it with a manual clock). Staleness is at most 60 s: an entry read at t is used while now < t + 60 s. `Invalidate(id)` after the audited save of Suspend and Approve; a generation counter stops a read that was in flight during an invalidation from re-inserting the old value. A missing account is cached as `null` (not suspended; unchanged behaviour). Bounded at 10,000 entries (expired ones purged, then cleared).
- **Limitation, several API replicas:** the cache is per process. A suspend or approve handled by replica A invalidates only A's entry; replica B keeps its entry up to 60 s, which is the spec's bound. Today the deployment is one API container. A shared cache (Redis) or a per-customer "security stamp" claim checked against the database would make it immediate everywhere; not built (no new dependency, out of scope). A status written straight to the database (SQL, a migration) is likewise seen after at most 60 s.
- Login: the Client account is read after the password was verified (it already was, for the `client_id` claim), so a wrong password does the same work for every account and answers the same 401; an unknown e-mail is as before (no password hash is computed for it: a pre-existing timing difference between "unknown e-mail" and "known e-mail, wrong password" that this story does not widen or close). The 403 consumes one permit of the same `auth` policy as any request; nothing is logged beyond the existing audit (no new log line).
- Test support: `TestClients.SetClientStatusAsync` (writes the status directly) now also calls `Invalidate`, like an admin decision, so tests that need the state at once keep working; the 60 s test writes with the context directly to prove the expiry.
- Existing tests that assumed a Suspended customer could still use the API with a stale token were rewritten to the new rule: addresses and profile (403 with the code; staff view shows the data unchanged), the visitor prices after suspension (stale token 403, a signed-out visitor sees the visitor price), a Pending customer in place of a Suspended one where the test was about order of validation. The controller-level defences (locked registration fields, eligibility 403) stay and are still exercised through staff-placed orders and the Pending state.
- Bundle (O-0): no script or CI step ever enforced 237,975 B (it lived in the work-item orders and the specs' "60 kB growth" criteria); the gate is now stated in `docs/tests/README.md` and `project.md` section 5 and enforced by the new `test/bundle-size.sh` (exit 1 above 300,000 B). Old figure 237,975 B (headroom 977 B at 9.5), new cap 300,000 B; MRV-9.9 build 236,810 B total, first visit of `/` 124,300 B (initial scripts, module preloads and stylesheet gzipped per file; fonts and lazy chunks excluded).
- `test/client.sh` replaces the `/tmp/ct.sh` helper in the docs: it keeps the exit code of `ng test` and fails on an `Errors` line.
- O-4 (Security low 3): a database error inside the gate (the status lookup throws) is **not caught**: the generic exception handler answers 500 and the request never reaches the endpoint, so the gate fails closed. Kept on purpose: answering as if the customer were Approved would let a suspended customer through during a database fault, and answering 403 "suspended" would be a false statement. Only Client tokens with a `client_id` reach the lookup, so visitors, Employees and Admins are unaffected. Tests: `AFailingStatusLookup_InTheGate_Answers500_NeverLetsTheRequestThrough` (a cache subclass whose lookup throws: 500 on the profile and the catalogue, 200 for a visitor and an admin, back to 200 when the lookup recovers) and `AFailingDatabaseRead_ThrowsOutOfTheCache_AndCachesNothing` (a disposed context: the exception propagates and the entry dictionary stays empty). `ClientStatusCache` is therefore no longer sealed and `GetStatusAsync` is virtual (test double only).
- O-4: defence in depth is tested by the real bypass, the stale window: the cache says Approved, the database says Suspended, so the gate lets the request through and the inner rules refuse (profile PUT: 403 with the locked-field message, not the gate's code; quote request: 403 "Client account is not active."); after 60 s the gate answers with the code. Spec AC-2 now says "every request carrying that token (public endpoints included; /api/auth/* exempt)".
