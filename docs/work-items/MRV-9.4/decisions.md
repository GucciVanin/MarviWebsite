## Worker decisions (2026-10-30)

### Check-digit rules, confirmed against official sources (fetched 2026-10-30)
- **Alphanumeric CNPJ, official:** Receita Federal, "CNPJ Alfanumerico" perguntas e respostas (PDF), https://www.gov.br/receitafederal/pt-br/centrais-de-conteudo/publicacoes/perguntas-e-respostas/cnpj/cnpj-alfanumerico.pdf (text extracted with pdftotext) and the news item https://www.gov.br/receitafederal/pt-br/assuntos/noticias/2024/outubro/cnpj-tera-letras-e-numeros-a-partir-de-julho-de-2026 . Confirmed: format `AA.AAA.AAA/AAAA-DV`, positions 1-12 digits 0-9 or letters A-Z, the two DV positions numeric; entry into production from July 2026; current numeric CNPJs and their DVs stay valid (questions 2, 4, 15); filiais may have letters in the order number (17); DV by módulo 11 with every character converted to ASCII minus 48 ("A" = 17), weights `5 4 3 2 9 8 7 6 5 4 3 2` for the first DV and `6 5 4 3 2 9 8 7 6 5 4 3 2` (first DV appended) for the second (question 14). Worked example: `12.ABC.345/01DE` gives sum 459, remainder 8, DV1 = 11 - 8 = 3; second sum 424, remainder 6, DV2 = 5, so `12.ABC.345/01DE-35`; this exact number is a unit test (`RegistrationRulesTests`, client `registration.spec.ts`, runtime suite).
- **What the Receita text does not say:** the rule for a remainder of 0 or 1 (DV 0) and the refusal of a repeated-character number. Both are the long-standing módulo 11 convention for the CNPJ and are kept (tests: `00.000.000/0001-91`, a real-format head-office number, validates; `00000000000000` is refused).
- **CPF:** the official Receita Federal page with the CPF algorithm could not be retrieved (the searches returned only secondary sources; the normas.receita.fazenda.gov.br annex fetch returned no text; the Paraná Fazenda page covers only the state registration). The rule used is the standard, widely published one and is **not** official-source-confirmed: first DV over the 9 base digits with weights 10..2, second DV over the 10 digits with weights 11..2, remainder < 2 gives 0 else 11 - remainder, repeated-digit numbers refused. Unit-tested on the usual public examples (`111.444.777-35`, `529.982.247-25`, `280.012.389-38`). **Follow-up for the owner/Captain:** have someone confirm the CPF rule against the Receita page once reachable; it does not change behaviour for any real CPF.
- **Spec correction:** none needed for the CNPJ (the spec text matches the official rule); one clarification: the Receita does not itself state "repeated digits invalid" or the 0/1 remainder rule (see above).

### Behaviour decisions
- **Owner sees the CPF masked, not in full (stricter than the spec's "shown in full only to the owner and the admin").** The profile API returns `cpfMasked` and `hasCpf` only, so the full number never reaches any screen except the audited admin "Mostrar CPF"; the form keeps a stored CPF when the field is left blank, and a Pending customer who wants to change it types the whole number again.
- **Suspended customers edit nothing** (spec AC-4): any registration change by a Suspended customer is 403, phone and invoice e-mail included. An unchanged save is fine. (The Reviewer found the first draft let them edit contact fields; fixed.)
- **Registration without an account type is a business account** (the API default; the page always sends one).
- **Duplicate CNPJ/CPF at registration answers 409 to an anonymous caller** ("CNPJ já cadastrado." / "CPF já cadastrado."), as the spec asks (it never says whose). This is an existence oracle for a given CPF; the registration endpoint is limited per client address by the `auth` rate limit (10 per 60 s by default). Accepted; a stricter policy would be a later decision for the owner.
- **Age is counted on the date in Brazil (UTC-3)**; a 29 February birthday counts as 18 from 1 March (conservative). The API tests pin the day (2026-10-30) through `IBrazilDate`.
- **Server pt-BR messages pass through the client error translator** when they contain an accented letter (the English Identity messages never do).
- **Production guard** now also requires `Privacy:CpfHashKey` (32+ characters, no example marker) and `DataProtection:KeysPath`, and refuses `DataProtection:Ephemeral`.
- **Keys:** compose mounts the named volume `marvi-dataprotection` at `/keys`; `deploy/Dockerfile.api` creates `/keys` owned by `$APP_UID` so the new volume is writable. `down -v` of a stack removes the keys together with its database, consistent with no data. Documented in `docs/operations.md` section 7.

### O-5 decisions (Security and Reviewer return, 2026-10-31)
- **Duplicate CPF/CNPJ answer is one generic text** ("Não foi possível concluir o cadastro com estes dados. Se você já tem conta, entre ou fale conosco.") on registration, on `PUT /api/client/profile` and on the admin edit, for CPF and CNPJ alike, and identical whether the check or the unique index caught it. The unique constraints stay. Registration now has its own tighter limit (5 per 60 s per client address; the shared sign-in limit stays 10), the profile save and the CPF reveal have their own limits.
- **Owner option, not done:** resolve duplicates at approval time (accept the registration whatever the CNPJ/CPF, and let the admin who approves see "this number is used by customer C-000123" and decide). That would remove the oracle entirely (nothing the anonymous caller sees depends on other accounts) at the price of dropping the unique indexes and moving the duplicate rule into the admin's hands. The owner may veto the generic answer in the PR and ask for it.
- **Key ring and hash key:** key-ring backups apart from database backups; certificate protection (`ProtectKeysWithCertificate`) is a pre-production follow-up, not implemented. The hash-key canary (a keyed fingerprint in `app_settings`) refuses a Production start on a changed key.
- **Audit trail:** the birth date is not written to audit snapshots (only that one is set, and whether it changed); the CNPJ stays (public registry data). "Mostrar CPF" needs a reason, stored in the entry.
- **Invisible characters** (control, line/paragraph separators, Unicode format characters such as zero-width, bidirectional marks and the byte-order mark) are refused in the display name and every registration text field.
- **A Suspended customer can no longer rename the company** (MRV-2.2 allowed it): the registration form is read-only for them, with the reason; the API answers 403. Noted in project.md and the PR notes.
- **Validation answers name the field:** a 400 for registration data is a list of `{ field, message }` (API names such as `cnpj`, `birthDate`, `companyName`), and the SPA shows each message under its control. Identity's own password errors stay plain strings.
