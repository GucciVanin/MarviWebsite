# decisions
Slice 8.3 of MRV-8 (issue #48): forms and field alignment. Goal: `form-column-width`, `form-row`, `form-left-edge` and `card-height` at 0 in every group at all eight widths.

## Result (measured, dev stack rebuilt with `docker compose ... up -d --build client`)
- Layout audit, whole run: 305 violations (after 8.2) to **235**. `form-column-width` 46 to **0**; `form-row`, `form-left-edge` and `card-height` were already 0 on real pages after 8.2 and stay 0. The three public groups stay at **0**. Remaining by rule (all 8.4/8.5, none form rules): `exceeds-parent` 70, `overflow-element` 69, `overflow-page` 32, `wrapped-control` 64. By group: admin 157, employee 36, client 24, client-wholesale 18.
- Text zoom 200% (`--text-zoom 2`, 320 and 375, all groups, emulation): 0 form rules. Public groups: 67 `wrapped-control` and 6 `covered-text` (same as after 8.2, reported not gated); portal overflow and wrapping is 8.4/8.5.
- Self-test: 19 fixtures, 0 failed (audit untouched). Client suite 1135 pass (no spec changed: CSS only). Bundle, gzip -9 per file over all js+css, island excluded: **198,878 B** (Worker's count; 8.2's Worker count was 198,839 B, Testing's method gave 199,714 B), +39 B.
- Lighthouse (Docker femtopixel/google-lighthouse, dev stack): accessibility **100** and CLS **0** on home, storefront and contact, mobile and desktop. Performance (not gated): mobile 60 / 65 / 70, desktop 98 on all three.

## Cause and fix (box model, no rule weakened, no exemption added)
- All 46 findings were one cause: `.toolbar` is a flex-wrap row whose `.field` children were sized by their content, so when a row wrapped on a phone the stacked fields had unequal widths (116 to 324 px in one column), and a field alone on a wrapped row at 768 px was narrower than the full-width fields below it. Fix in `_components.scss`: `.toolbar .field { flex: 1 1 min(100%, 14rem); min-width: 0 }`. Fields that share a row split it evenly; once the row cannot hold two 14rem fields every field takes the whole row, so stacked fields are always one width and one left edge. Every admin, employee and client-portal filter bar, inline editor and the product picker use `.toolbar > .field`, so this rule covers them; no template changed. Not covered by it: the stacked `.field` forms (client profile, login, register, contact), which are plain grids already aligned (audit 0); the audit visits default states only, not editors opened by clicks.
- Checkbox/radio inside `.field`: the global `input { width: 100% }` pushed the box to the far right of a now-wider field (seen by eye at 768 px on the catalog forms). `.field` checkboxes and radios are `width: auto; flex: none` and a label that wraps one is a flex row with a gap. This also removed 24 `exceeds-parent` findings in the admin portal.

## Not done / decisions for the owner
- Owner confirmation needed: O-1 mentions a new `.form-grid` / `.form-actions` system. I extended the existing `.toolbar`/`.field` instead (every toolbar form uses them, zero template churn, zero audit findings left). Loose buttons after a toolbar (Save/Cancel) still flow as inline-flex siblings with the 8.2 `nowrap`; they pass `button-row-height` and `wrapped-control`. A `.form-actions` wrapper is not added: it would touch about 20 templates for no measured defect. Reversible: say so and it goes in with 8.4/8.5.
- Visible change: toolbar fields now stretch to fill the row (a lone search field spans the card instead of its content width; 3 fields in a row are equal). Checkbox fields are full-width rows with the box beside its label.
- Hints and errors: the client profile form (a plain `<form>`, not a toolbar) has a hint and an empty `role="status"` message inside a `.field`, and the contact form has per-field errors. Fix: `.field > p` has no margin and an empty `.field > p` is taken out of flow (visually hidden, still in the DOM for assistive technology), so it reserves no row. Contact's `.field__control` errors were not changed (public groups 0). Worker-verified by DOM only in the default state; long error messages not exercised.
