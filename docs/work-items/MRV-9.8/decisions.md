# decisions
- Spec decisions of the Captain (2026-11-03, reversible): one domain class `ProductRules` is the only validator; create = `POST /api/admin/products/with-setup` (the legacy `POST` is removed); `PUT` validates the whole product; one narrow exception for `IsActive`-only edits; the import is brought under the same rules; nothing stored is silently rewritten (a data check lists the broken rows).
- Worker 2026-11-03, naming: `ProductSetupRules` -> `ProductRules` (file renamed with git mv; the old `ProductRules` with `MaxSkuLength = 64` and `MaxNameLength` was deleted and its name limit moved in); `ProductSetupProblem/Input/Plan/Price/Stock` -> `ProductProblem/ProductInput/ProductPlan/ProductPrice/ProductStock`; `UpsertProductRequest` (C# and TypeScript) -> `UpdateProductRequest` because it is now only the edit body, with nullable text fields so a missing SKU or name is a field problem and not a bare ASP.NET 400. The JSON of a problem is unchanged: `{field, message}`.
- **IsActive-only exception (Reviewer may challenge).** `PUT` is accepted without validation when `request.IsActive != stored.IsActive` and every other field equals the stored one after the usual cleaning (trimmed SKU, name, description and image; same category id; the same attributes once trimmed with blank rows dropped). Only `IsActive` is written (the other fields are not rewritten or "cleaned"); the audit entry is the normal `Update`. A request with no difference at all is NOT the exception: it is validated (so saving an unchanged broken product from the form shows what to fix). Reasons: a product can always be deactivated or reactivated without first correcting data the owner may not have time for, and nothing else slips through. Tests: positive (only `IsActive`, both directions, every other field unchanged afterwards) and negative (rename plus `IsActive`, no change at all, long description plus `IsActive`: 400 and nothing stored). The edit form mirrors it (`isActivationOnly`), otherwise the client would block what the API accepts.
- **The import stays all or nothing.** The spec says failing rows are "reported per row ... never saved". The existing contract of the import (MRV-2.1) is that a file with any error imports nothing; kept, so a row that breaks a product rule is reported with its line, SKU and field in the dry run and the real import and the good rows of the same file are not saved either (a partial import would leave a half-applied file the admin cannot reason about). The report is `ProductImportErrorDto(line, message, sku, field)`; the 400 body of a refused file is still the report.
- **The import checks the product as it would be stored.** The planner gets the stored description, image and attributes (`ImportCatalog.ExistingProducts`) and runs `ProductRules.Check` on the result: a blank cell keeps the stored value, attribute columns replace a stored attribute with the same name ignoring case (before, `Marca` and `marca` could sit side by side), and the merged set must still be at most 30. Consequence: a CSV row for a STORED product that breaks the rules (long description, `http` image, too many attributes) is refused until the product is fixed, like an edit. Chosen so that "old data cannot slip around the rules"; the alternative (checking only the cells of the row) was rejected because the merge could produce a product no other path may save.
- Import price and stock cells go through the same price (above zero, two decimals, within the column) and quantity (0 to 1,000,000) rules as create. Behaviour change: a price of 0 in a CSV used to be accepted ("0 or more") and is now refused; the parse errors ("not an amount", "not a whole number") keep their own messages. The import's own limits are gone: SKU 64 -> 40 (3 minimum, shape), name 2-200 and no control characters, attribute name header limit 64 -> 60, description 2,000, values 1-200 without newlines, at most 30 attributes. The messages of the shared rules are pt-BR (the same text the form shows); the file-level messages of the importer (unknown column, unknown category, price parse...) stay English as before, so a report mixes both.
- **Category is a rule for every path (Captain ruling O-1, 2026-11-03).** "One path" means the same verdict for the same input, so `ProductRules.Check` requires a category (`categoryId`: "Escolha a categoria do produto.") for create, `PUT` and the import alike; the database check that it exists stays in the callers. Import: a new SKU needs a `category` cell; a stored SKU may leave the cell blank only if the stored product has a category (the planner takes the stored one from `ExistingProduct.CategoryId`). `PUT` with no category is a 400. The data check lists stored products without a category (`categoryId`). The IsActive-only exception is unchanged, so a category-less product can still be deactivated. The client form requires the category for edits too (no more "Sem categoria" option). Contract table: case "no category chosen". Test fixtures that need a category-less product (runtime "Item Sem Categoria") clear it with SQL, standing for a product stored before the rule.
- **All-or-nothing import accepted by the Captain (O-1):** the spec says "per row ... never saved"; the MRV-2.1 contract (any error imports nothing) is kept and stated as a deviation in pr-notes.md.
- `PUT` conflict and not-found bodies: a taken SKU is `409 [{field: "sku", message: "SKU já existe."}]` (it was the English string "A product with this SKU already exists."), an unknown category `400 [{field: "categoryId", ...}]`, a race the checks could not see `409 [{field: "form", ...}]`, like create. The status codes are unchanged.
- **Data check = an admin-only endpoint**, `GET /api/admin/products/data-check`, not documented SQL: the rules include the character classes and attribute rules that are impractical in SQL, the endpoint reuses `ProductRules.Check` so it cannot drift from the validator, and it is smaller than a script that re-implements them. It returns `{checked, broken, products: [{id, sku, name, problems: [{field, message}]}]}`, read-only (no tracking, no save), no paging (a catalogue is hundreds to a few thousand rows). Tested with rows built directly in the database; it also goes in the authorization matrix. `docs/operations.md` section 8 shows the two curl commands and says to run it before the production migration.
- **Client/server comparison (AC-5): one contract file.** `client/src/app/features/admin-portal/catalog/product-rules.contract.json` holds the limits and a table of cases (field, text built as prefix + text x repeat, valid yes/no). It lives under `client/` because the client suite runs in a container that mounts only that folder; the API test finds it by walking up to `Marvi.slnx`. `SingleProductPathTests` runs every case through `ProductRules`, create, update and the import (same verdict each time, the same field named) and compares the limits with the constants of `ProductRules`; `product-rules.contract.spec.ts` runs every case through the form's rules and compares `PRODUCT_LIMITS`. Building it found a real mismatch: the API refuses every `Cf` format character (soft hyphen U+00AD, bidi isolates U+2066...) and a line separator, the form's `hasInvisible` listed only some ranges; it now uses `\p{Cc}\p{Cf}\p{Zl}\p{Zp}` per UTF-16 unit, like the API.
- Client: `legacySkuMax`, the "SKU kept as it was" and the "description/image/attributes left as stored are not checked" leniencies are removed from `validateProduct`; an edit follows the same rule as a create, category included (see above). The panel shows the API's field messages for a refused edit exactly as for a create (`serverProblems`), including the 409 on the SKU.
- Tests: `TestClients.PostProductAsync/CreateProductAsync` now create through `with-setup` and need a category, so they use a shared category "Test products" (`EnsureTestCategoryAsync`); `PublicStatsTests` creates it before its first reading. The test `Products_RejectUnknownCategory_ButAllowNone` became `Products_RejectUnknownAndMissingCategories_OnCreateAndEdit_Alike` (an unknown or missing category is a 400 on create and on edit). Removed: `AProductMadeByTheCsvImport_WithALongDescription_CanBeDeactivatedThroughTheEditEndpoint` (the import now refuses a 2,500-character description; the case of a broken stored product is covered by the IsActive-only test, which builds the row directly). Planner tests moved from one-character SKUs to three-character ones and their expected messages follow the shared rules.
- `deploy/seed-demo.mjs` creates through `with-setup` with empty prices and stock (the prices and the stock with a reorder point are still set through their own endpoints, as before). The runtime suite's product fixtures do the same; its "Item Sem Categoria" fixture is created in a category and then edited to have none (the one way to have a category-less product).
