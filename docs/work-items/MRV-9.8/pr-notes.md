# PR notes MRV-9.8 (issue #60)

Closes #60. Spec: `docs/specs/MRV-9.8-single-product-path.md`.

**Behaviour changes to review**
- `POST /api/admin/products` is removed (404/405). Create is `POST /api/admin/products/with-setup` only; the SPA service, tests, `deploy/seed-demo.mjs`, the runtime suite and the docs were moved to it. A create needs a category (as the guided form always did).
- `PUT /api/admin/products/{id}` now validates the **whole product** with the same `ProductRules` as create: SKU 3-40 (letters, digits, `- _ .`; it was up to 64 of anything), name 2-200, description up to 2,000, https image up to 500, at most 30 attributes, no control or invisible characters. The MRV-9.5 "validate only the fields that changed" leniency is gone: a stored product that breaks a rule cannot be saved until it is corrected. Errors are `[{field, message}]` in pt-BR, also for a taken SKU (409) and an unknown category (400); before, these were plain English strings.
- **One exception, for the Reviewer to challenge:** a `PUT` whose only difference from the stored product is `IsActive` is accepted without re-validating, so any product can still be deactivated or reactivated. Anything else with it (a rename, a changed description, no change at all) is validated. The edit form mirrors it.
- **CSV import** runs every row through `ProductRules` on the product as it would be stored. A failing row is reported as `{line, sku, field, message}` in the dry run and in the real import (the screen shows line, SKU and field) and the file is still all or nothing: nothing is saved when any row fails, the good rows of that file included. Consequences: SKU limit 64 -> 40 and minimum 3, name minimum 2, description limit 2,000, attribute header limit 64 -> 60, at most 30 attributes, values without line breaks, a **price of 0 is refused** (it was accepted), stock above 1,000,000 is refused, an attribute column replaces a stored attribute with the same name ignoring case (it used to sit beside it), and a CSV row for a stored product that breaks the rules is refused until the product is fixed.
- New read-only `GET /api/admin/products/data-check` (admin) lists stored products that break the rules. **Run it, and fix what it lists, before the production migration** (`docs/operations.md` section 8). Nothing stored is rewritten.
- Client: no legacy SKU or "unchanged field" leniency in the form; the form's invisible-character check now matches the API (soft hyphen and other format characters were accepted by the form and refused by the API). `product-rules.contract.json` (limits and a table of cases) is read by an API test and a client spec so the two sides cannot drift.
- **Category is required everywhere** (create, `PUT`, import: a new SKU needs a `category` cell; a stored SKU needs a stored or given one) and the data check lists stored products without one. A category-less product can still be deactivated (IsActive-only exception). The edit form drops the "Sem categoria" option.
- **Spec deviation, accepted:** the import is all or nothing (any failing row stops the whole file, as since MRV-2.1) rather than skipping only the failing rows; the failing rows are reported per row with line, SKU and field.
