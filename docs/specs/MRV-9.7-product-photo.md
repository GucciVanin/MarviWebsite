# MRV-9.7 Product photo: upload on creation, shown as the display photo

**Goal.** When an admin creates (or edits) a product they can include a photo, which becomes the product's display photo on the storefront, in carts and quotes, and in the admin lists, next to all the product information.

**Owner input (2026-11-03).** "When the product is being created we should have the option to include a photo, which will be the display photo. Along with all the necessary product information." (Replaces the earlier image-URL field; MRV-9.5 left the URL only stored because the CSP blocks external images and the storefront never rendered one.)

**Facts (Captain, code read 2026-11-03).** `Product.ImageUrl` exists (free https URL, MRV-9.5). nginx proxies `/api/` to the API and its CSP is `img-src 'self' data:`; no storefront template renders a product image. The SPA and the API share one origin through nginx, so images served under `/api/...` need **no CSP change**.

**Decisions (Captain, reversible).**
- Photos are **uploaded files stored on the server** (a persistent Docker volume mounted into the API, like the Data Protection keys), served anonymously and read-only at `GET /api/public/media/products/{name}` with long-lived cache headers (`Cache-Control: public, max-age=31536000, immutable`), `X-Content-Type-Options: nosniff` and the stored content type. Names are a random 128-bit token plus the extension, never the original filename.
- Upload-first flow keeps creation atomic: the panel uploads the file to `POST /api/admin/media/product-photos` (Admin only, multipart, rate limited), which returns a short-lived `photoToken`; `with-setup` and the product update accept `photoToken`, which links the stored file to the product in the same transaction. Uploads not linked within 1 hour are deleted by a background cleanup; replacing or removing a photo deletes the old file.
- Allowed: JPEG, PNG, WebP. Refused: everything else (SVG, GIF, HEIC, PDF, polyglots). Size at most 5 MB, dimensions between 400x400 and 6000x6000 px, content verified by **magic bytes and a header parse**, not by extension or the client's content type. Metadata (EXIF/GPS) is not stripped in this story (no image-processing dependency is added); logged as a follow-up. No server-side resizing or thumbnails in this story: the storefront shows the file in a fixed-ratio box with `object-fit: cover`, `width`/`height` attributes (no layout shift) and `loading="lazy"` below the fold.
- One display photo per product. The old free-text image URL field is **removed** from the panel and from the API request; existing `ImageUrl` values are set to null by the migration (documented), because external URLs can never display under the CSP. The column keeps storing the relative media path.
- "All the necessary product information": the panel keeps SKU, name, category, description, active flag, attributes, prices and opening stock (MRV-9.5), and the storefront card/detail shows the photo, name, SKU, category, description and the attributes (brand, unit, case quantity, volume...) so what the admin enters is what customers see. A missing photo shows a neutral placeholder of the same size.

## Acceptance criteria
- AC-1 `POST /api/admin/media/product-photos` accepts one file (Admin only; 401/403 otherwise; rate limited by an existing policy shape), validates type by magic bytes, size and dimensions, refuses everything else with a pt-BR field message (no value echo), stores it under a random name on the configured media volume and answers `{photoToken, previewUrl}`.
- AC-2 `with-setup` and the product update take an optional `photoToken`; linking happens in the same transaction as the product save; an unknown, expired, already-used or other-admin token answers 400 on field `photo`; replacing a photo deletes the previous file; `removePhoto: true` clears it. Unlinked uploads older than 1 hour are removed by the cleanup, with a test.
- AC-3 `GET /api/public/media/products/{name}` serves only files inside the media folder (names validated against the token pattern), 404 otherwise, correct content type, `nosniff`, long cache; a path-traversal test set (`..`, encoded, backslash, absolute) all answer 404.
- AC-4 The product panel replaces the image URL field with a file chooser (drag-and-drop optional): preview from the **same-origin** upload URL, file name and size, a remove button, pt-BR validation messages (type, size, dimensions) before and after upload, a busy state, keyboard operability and labelled controls; on edit the current photo is shown and replaceable.
- AC-5 Storefront cards, product picker, basket and quote/order lines show the product photo (or the placeholder) with alt text (the product name), fixed aspect-ratio boxes (CLS stays 0) and `loading="lazy"` except the first row; the admin product table shows a small thumbnail.
- AC-6 The storefront card/detail also shows the description and the attributes the admin entered (labelled, escaped).
- AC-7 The CSP is unchanged (`img-src 'self' data:`) and every displayed photo loads under it (checked in the browser on the dev stack); nginx allows request bodies up to 6 MB for the upload location only, nothing else widened.
- AC-8 The migration sets existing `ImageUrl` values to null and the docs say so; the media volume is declared in `deploy/docker-compose.yml` and `docs/operations.md` (path, permissions, backup alongside the database, growth); the Production guard refuses to start without a configured media path.
- AC-9 API tests (valid JPEG/PNG/WebP; fake extension; polyglot/SVG/GIF; oversize; undersize; wrong dimensions; traversal set; roles; token reuse and expiry; cleanup; file link rolled back when the product save fails), runtime tests on Postgres with the real volume, client specs (chooser, validation, preview, edit/replace/remove, cards with and without photo), layout audit + axe + 200% text with the chooser and cards covered (gated categories 0), Lighthouse a11y 100 and CLS 0 on `/storefront`, three identical runs, **with exit code 0 and no "Errors" line from the client suite**; bundle within the gate the owner sets.
- AC-10 `CONTEXT.md` (**Product photo**), `project.md`, `architecture.md`, coverage maps updated; the privacy and ops docs mention that uploaded photos may carry metadata until stripping is built.

## Out of scope
Several photos per product or galleries, zoom, server-side resizing and thumbnails, CDN, metadata stripping, background removal, importing photos by CSV, customer-uploaded images.
